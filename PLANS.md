## Цель MVP

Минимальный, но полностью рабочий продукт **без ручных обходов через API**:
заявитель регистрируется и создаёт/заполняет/отправляет заявку; администратор управляет
заявками, назначает экспертов и финализирует статус; эксперт открывает назначенную заявку,
оценивает по критериям и пишет рецензию; заявитель видит статус и рецензии; PDF выгружается
любой ролью; публикации читаются как лента обратной связи.

### Критерии приёмки

- Заявитель: регистрация (с обязательным соглашением) → создание заявки → заполнение
  (основное, команда + согласия, план, бюджет, материалы) → отправка → просмотр статуса/рецензий.
- Админ: создание заявки с привязкой владельца; редактирование, смена статуса, назначение
  N экспертов (по умолчанию 2), управление справочниками и публикациями; PDF.
- Эксперт: список назначенных заявок → просмотр (в т.ч. файлы) → оценка по критериям
  (итоговый балл считает сервер) → текст рецензии и вердикт.
- Согласия: загрузка/скачивание/удаление; без согласия участник не проходит валидацию.
- PDF доступен всем ролям; шаблон совпадает с UI.
- Домашняя страница публична: лента публикаций + контакты; вход/регистрация.
- Ручной E2E-прогон в трёх ролях без ошибок; коллекция Postman.

## Принятые продуктовые решения

1. **Вердикт эксперта** — рекомендация; финальный статус заявки ставит **администратор**.
2. **Согласие обязательно.** Если у участника нет файла согласия — показывается диалог
   с ошибкой и выбором «подтвердить / отмена». При подтверждении участники без согласия
   удаляются из заявки, затем идёт проверка валидности: **≥ 1 участник и совершеннолетний координатор**.
3. **Точка входа** — публичная домашняя страница: лента публикаций/новостей + место под
   контактную информацию организации; вход/регистрация слева сверху.
4. **Админ создаёт заявки.** В модалке создания — привязка владельца (пользователя),
   чтобы заявка не «висела» на админе.
5. **Эксперты на заявку** — несколько, **по умолчанию 2**; параметр задаётся в настройках
   конкурса. Критерии оценивания настраиваются в конкурсе. Конкурс создаётся на сезон подачи;
   направления и критерии привязаны к конкурсу. Во фронтенде `tenders` именуется **«Конкурс»**,
   а `application_reviews` — **«Экспертиза»** (вердикты — редактируемый справочник `review_statuses`).
6. **PDF** — доступен всем ролям, включая эксперта.
7. **Публикации** — канал обратной связи админов с пользователями (лента новостей).
8. **`change_logs`** — не трогаем (использование отложено).

### Дополнительные требования

- **Регистрация — соглашение.** Обязательная галочка «Соглашение»: просто кликнуть и
  поставить нельзя — по клику открывается модальное окно с текстом политики. На время
  разработки/отладки галочка ставится **долгим нажатием** (hold). Без галочки submit заблокирован.
  Текст — на основе `Privacy-policy-example.tsx` (пользователь предоставит финальную редакцию).
- **Подвал/футер** — дата, ссылки, страница «О проекте» (`/about`).
- **Шапка меняет цвет по роли** (админ / эксперт / заявитель) — визуальная индикация текущей роли.

## Блоки MVP

### Блок 1 (v1.10.0) — Каркас, согласия, регистрация-соглашение — ВЫПОЛНЕН

- Общий каркас `AppLayout` (навигация и цвет шапки по ролям: админ — серый, эксперт — зелёный,
  заявитель/гость — синий) и публичный `PublicLayout`; общий футер.
- Публичная домашняя `/` (лента публикаций с пагинацией + контакты), `/about`, `/privacy`.
- Согласия участников (загрузка/скачивание/удаление) + `hasConsent`/`consentsCount`.
- Проверка готовности заявки к отправке (`/validation`) и диалог удаления участников без согласия.
- Обязательное соглашение при регистрации (модалка с прокруткой; в dev — удержание).
- Кнопка «Отправить на проверку» в карточке заявки (админ).

- Общий каркас `AppLayout`: шапка с **ролевым цветом**, футер (дата, ссылки, контакты),
  навигация по ролям вместо единственного `AdminLayout`.
- Публичная **домашняя страница** (`/`): лента публикаций + блок контактов; вход/регистрация.
  Лента — из уже существующего `GET /api/posts` (опубликованные).
- Страница **«О проекте»** (`/about`).
- **Согласия**: UI загрузки/скачивания/удаления в секции команды + `consents` в API-клиенте.
- **Правило валидности заявки** (backend, переиспользуемое): ≥ 1 участник и совершеннолетний
  координатор; отсутствие согласия у участника — ошибка с перечнем участников.
- **Регистрация**: модалка соглашения (текст), «hold-to-agree» в dev, блокировка submit.
- `HomeRedirect`/`RegisterPage`/`LoginPage` — под новый каркас и точку входа.

- Область заявителя: список «Мои заявки», создание, редактирование.
- **Рефакторинг**: общий `ApplicationEditor` (основное/команда/план/бюджет/материалы),
  переиспользуемый заявителем и админом — без копипасты с админской карточкой.
- Отправка на проверку с проверкой валидности; диалог по согласиям (см. решение 2).
- Заявитель видит статус заявки, рецензии и вердикт эксперта; после отправки — только чтение.
- Админ: кнопка «Создать заявку» + выбор владельца.
